Decision logic is where behaviour becomes hardware

Most behavioural Verilog is decision logic: choose an output based on inputs. Verilog offers two constructs for it, if/else and case, plus two wildcard variants, casez and casex. They look interchangeable and are not. Each encodes a different priority structure, and each has a characteristic failure mode.

The example writes the same priority encoder three ways — if/else, casez, and an intentionally incomplete block that infers a latch — and proves that the first two agree on all sixteen inputs.

if/else: a priority chain

An if/else if chain tests conditions in order and executes the first true branch. In hardware it becomes a chain of multiplexers with the first condition at the highest priority. That is the natural description of a priority encoder, where the highest-numbered request wins.

Priority by ordering
if      (req[3]) code = 3;
else if (req[2]) code = 2;
else if (req[1]) code = 1;
else if (req[0]) code = 0;

Order is meaning. Swap two branches and the priority changes, silently. This is why a priority chain should be arranged in a deliberate order and commented, not left in whatever order the conditions were typed.

case, casez, casex

Comparison of the case family
FormMatching ruleUse
caseExact four-state match. x matches only x, z only z.Instruction decode, state machines with fully specified encodings.
casezz and ? in either the expression or an item are don't-cares.Priority decoding, opcode matching with ignored bits.
casexx, z and ? are all don't-cares.Rarely. It hides unknown values that should have been caught.

casez is the useful wildcard form. casex is dangerous in verification because an x on an input — which usually means something is wrong — is treated as a match instead of a red flag. Many coding standards ban casex outright.

All three evaluate the items in order and execute the first match. So casez is also a priority structure: the first pattern that matches wins. In the example, 4'b1??? is placed before 4'b01?? precisely so that bit 3 dominates.

Incomplete assignment infers a latch

A combinational always @* block must assign every output on every path. If some path leaves an output unassigned, the only way the circuit can reproduce the simulation's "keep the old value" behaviour is to store it. Synthesis therefore inserts a latch:

Latch inferred
always @* begin
    if (en)
        q = d;      // when en = 0, q keeps its previous value
end

Latches are not automatically wrong — a transparent latch is a legitimate element — but an unintended latch is a bug. It is level-sensitive, it complicates timing analysis, and it usually means the designer forgot an else. The example includes this block deliberately so the behaviour can be observed rather than described.

The standard fix is a default assignment before the conditional structure, or a complete else and a default. Assigning a default at the top of the block guarantees that every output has a value on every path, which removes the storage requirement.

Line by line: the if/else encoder

  • valid = 1'b1; is the default. It is overwritten in the final else when no request is present. Setting a default first is the habit that prevents latches.
  • if (req[3]) code = 2'd3; gives bit 3 the highest priority. Every later test only runs if this one failed.
  • The final else handles req == 0000, setting code to 0 and valid to 0. That is the only case in which valid is 0.

Line by line: the casez encoder

  • valid = |req; uses a reduction OR, so valid needs no branch logic at all.
  • 4'b1??? matches any pattern whose top bit is 1. Because it is first, it wins over every lower request.
  • 4'b01??, 4'b001? and 4'b0001 form the descending priority chain. The patterns are mutually exclusive in their leading-1 position, so the first-match rule is unambiguous.
  • default: code = 2'd0; covers 0000. Without it, code would be unassigned for that pattern and synthesis would infer a latch.

The first sixteen rows are the truth table. The if and casez columns agree on every pattern, which is what the mismatches: 0 line confirms. The code follows the highest set bit: 0001 gives 0, 0010 gives 1, 0100 gives 2, 1000 gives 3, and mixed patterns such as 1010 give 3 because bit 3 wins.

The last three lines show the latch:

  • en=1 d=1 -> q=1: the latch is transparent and follows the data.
  • en=0 d=0 -> q=1 (held): the enable is low, so the output ignores the new data and holds the previous value. This is storage, created by an incomplete assignment.
  • en=1 d=0 -> q=0: the latch reopens and follows the data again.

Pragmas and SystemVerilog

You may see // synopsys full_case or // synopsys parallel_case in older code. These are comments interpreted by some synthesis tools, not part of Verilog-2001. full_case tells the tool that all cases are covered, so it need not infer a latch; parallel_case tells it that the items are mutually exclusive, so it need not build a priority chain. Both can change behaviour when the assumption is false, and both are unnecessary if the Verilog is written completely and unambiguously.

SystemVerilog adds unique, priority and inside, which express these intents as language features with simulation checks. They are not available in Verilog-2001 and are outside this course's toolchain. In Verilog-2001, the safe approach is: assign defaults, cover every branch, and test overlapping patterns.

Common mistakes

  • Forgetting the default assignment. One unassigned path is enough to infer a latch. Assign a default at the top of every combinational block.
  • Relying on case order without saying so. case is a priority structure. If the items overlap, the first match wins, and a reader may assume otherwise.
  • Using casex on data that can be x. An unknown input silently matches a wildcard instead of failing loudly.
  • Assuming casez ignores x. It does not; only z and ? are wildcards. An x in the expression does not match a ? item.
  • Writing overlapping casez items in the wrong order. The wildcard patterns must be ordered from most specific priority to least, or the wrong branch wins.
  • Using full_case to silence a latch warning. The latch was telling you the truth: a path was unassigned.

Revision points

  • if/else and case both build priority structures; the first true or first matching item wins.
  • casez treats z and ? as don't-cares; casex also treats x, which hides errors.
  • Every output must be assigned on every path of a combinational block, or synthesis infers a latch.
  • A default assignment at the top of the block is the simplest defence against latches.
  • full_case and parallel_case are tool pragmas, not Verilog-2001 features.
