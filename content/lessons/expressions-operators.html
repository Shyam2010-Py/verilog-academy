An expression has a width and a sign

In software, 15 + 1 is 16. In Verilog, the answer depends on the width and signedness of the operands and on the context in which the expression appears. A four-bit context gives 0. A 32-bit signed context gives 16. Both are correct; the language is telling you which hardware you asked for.

This topic is not a list of operators to memorise. It is a set of rules for predicting what an expression means before the simulator tells you. Once you can predict width, sign and precedence, most "strange" results become ordinary.

The table is useful, but parentheses are better. An expression such as a & b == c is legal and means a & (b == c) because equality binds tighter than bitwise AND. Most readers guess the other way. Write the parentheses you intend.

Width and signedness rules

  • An unsized decimal literal is 32 bits wide and signed.
  • The width of an expression is the maximum of its operands, unless the assignment context forces a narrower or wider width. Assignment propagates its width into the expression.
  • If any operand in an expression is unsigned, the expression is evaluated as unsigned. A signed operand next to an unsigned one loses its sign interpretation.
  • Arithmetic does not grow automatically. An 8-bit add produces eight bits; the carry out must be captured explicitly, for example by adding in a nine-bit context.
  • >> is a logical right shift (zero fill). >>> is arithmetic (sign fill) and is meaningful only for signed operands.
  • $signed() and $unsigned() change the interpretation of a value; they do not change its bits.

Line by line

  • a = 4'b1010; and b = 4'b0101; are exact complements, so a & b is 0 and a | b is all ones.
  • a ^ b is all ones because every bit differs. ~a is the four-bit complement, 0101.
  • &a is the reduction AND: 0 because not every bit of 1010 is 1. |a is 1 because at least one bit is 1. ^a is 0 because the number of ones is even.
  • a && b is logical AND: both vectors are non-zero, so the result is 1, not a vector.
  • a == b is 0. 1'b1 == 1'bx is x: a normal equality with an unknown operand cannot be decided. 1'b1 === 1'bx is 0 because case equality compares the actual values, and 1 is not x.
  • 4'd15 + 4'd1 is evaluated in four bits, so it wraps to 0000. The same sum in a five-bit context would be 10000.
  • s = -3 is stored as 1101. s >>> 1 shifts in the sign bit, giving 1110, which prints as -2. a >> 1 shifts in zero, giving 0101.
  • a[0] ? b : a uses bit 0 of a as the selector. It is 0, so the result is a.
  • -1 < 0 compares two signed 32-bit values and is true. 4'b1111 > 0 compares an unsigned four-bit value with a signed 32-bit zero; the unsigned interpretation wins, so 15 > 0 is true.

Common mistakes

  • Expecting arithmetic to grow. Addition and multiplication keep the operand width. Capture the carry deliberately.
  • Using == to detect x. x == x is x, not 1. Use === when you genuinely need to compare unknown values.
  • Mixing signed and unsigned operands. One unsigned operand makes the comparison or arithmetic unsigned. Declare signedness consistently or convert explicitly.
  • Using >> on a signed negative value. It zero-fills and changes the sign. Use >>> for arithmetic shift.
  • Confusing ! with ~. !a is one bit (logical negation); ~a is bitwise and preserves width.
  • Assuming / and % are cheap. Division by an arbitrary signal is expensive or unsupported in synthesis; division by a power of two is a shift.
  • Relying on precedence. Parenthesise comparisons inside bitwise expressions and mixed logical expressions.

Revision points

  • Expression width is the maximum operand width, propagated from the assignment context; arithmetic does not grow automatically.
  • An unsigned operand makes the expression unsigned. Unsized decimals are 32-bit signed.
  • == yields x when an operand is unknown; === compares known and unknown values exactly.
  • Bitwise operators work on vectors; logical and reduction operators produce one bit.
  • >> zero-fills; >>> sign-fills and belongs with signed values.
