Why hierarchy is not optional

A modern chip contains millions of gates. No engineer writes it as one flat file. Hierarchy lets a team divide the design into blocks that can be specified, implemented, verified and reused independently, then composed into a top level that is small enough to reason about.

Hierarchy is also how verification scales. If a leaf cell is proven against its own specification, the parent only has to prove that it wires the leaves correctly. Bugs are localised: a failure in a top-level test can be traced down the instance path to the block that produced it.

Top-down, bottom-up and mixed

Top-down

Start from the system specification, partition into blocks, then refine each block until the leaves are simple enough to implement. Interfaces are fixed early.

Bottom-up

Build and verify reusable leaf cells first, then compose them into larger blocks. Common for cell libraries and for teams reusing proven IP.

Mixed

Sketch the top-level architecture, implement critical leaves bottom-up, and iterate. This is how most real projects actually run.

Whichever method is used, the interface is the contract. A leaf cell that changes its ports forces every parent to change. That is why port lists are reviewed and frozen before implementation spreads.

Four full adders make a ripple-carry adder

The example has two levels. At the bottom, full_adder is built from primitive gates. At the top, rca4 instantiates four copies and chains their carries. This is structural modelling: no equation at the top level, only instances and wires.

Line by line

  • wire s1, c1, c2; declares the internal nets of the full adder. They are not ports, so the outside world cannot see them — but a simulator can, through a hierarchical name.
  • xor x1 (s1, a, b); instantiates a primitive gate. For gate primitives the output comes first, then the inputs. s1 is a XOR b.
  • xor x2 (sum, s1, cin); gives sum = a XOR b XOR cin, the correct sum bit for a full adder.
  • and a1 (c1, a, b); and and a2 (c2, s1, cin); form the two ways a carry can be generated: both inputs high, or the propagated sum high while the carry-in is high.
  • or o1 (cout, c1, c2); combines them: cout = ab + cin(a XOR b).
  • In rca4, full_adder fa0 (...) through fa3 are four separate instances. Each has its own internal s1, c1, c2; the names do not collide because they live in different instance scopes.
  • .a(a[0]) connects one bit of the parent vector to the scalar port. .cout(c1) of fa0 becomes .cin(c1) of fa1: that single wire is the carry chain.
  • The final cout is the carry out of bit 3, which is the carry out of the 4-bit addition.

Zero-delay structure

The primitive gates have no delays in this model, so the whole carry chain settles in the same simulation time step. The testbench's #1 gives a clean sample, but it does not model propagation delay. Real carry-chain timing is added by gate delays or, more accurately, by static timing analysis after synthesis. The ripple-carry topology itself is what this example teaches.

Hierarchy in the simulator

Every instance creates a scope. In this design the full path to the first carry wire is dut.fa0.c1: the testbench instance dut, the full-adder instance fa0, the internal net c1. Simulators use these paths for waveform viewers, hierarchical references and debug. They are also a useful mental model: if you cannot draw the path, you probably cannot explain which hardware you are looking at.

Hierarchy is not free. Every level adds names and a place for a connection error. Keep leaf cells small and their interfaces stable; keep parents shallow enough to review in one screen.

Common mistakes

  • Crossing carry wires. Connecting fa0.cout to fa2.cin instead of fa1.cin still elaborates and still simulates; only arithmetic tests catch it.
  • Reversing vector bit order. a[0] must feed the least significant full adder if sum[0] is the least significant result bit. Reversing both consistently is a different (but valid) convention; reversing only one is a bug.
  • Expecting structural code to model delay. Zero-delay gates switch instantly in simulation. Use gate delays or STA for timing.
  • Duplicating instance names. Two fa0 instances in the same parent are an error, even if they are in different generate branches (not used here).
  • Building hierarchy for its own sake. Every level should correspond to a real block with a stable interface. A hierarchy that mirrors source files rather than hardware becomes hard to verify.

Revision points

  • Hierarchy is created by instantiating modules; each instance is a separate copy of the hardware.
  • Top-down fixes interfaces early; bottom-up reuses verified leaves; mixed is the practical default.
  • Structural modelling contains instances and nets, not equations. It is the style of a gate-level netlist.
  • A full adder's carry is ab + cin(a XOR b); chaining carries builds a ripple-carry adder.
  • Hierarchical names such as dut.fa0.c1 identify one signal in one instance.
