Loops describe repetition, not time

A Verilog loop does not repeat an action over time. It repeats a piece of description, and synthesis unrolls that repetition into replicated hardware or a chain of operations. That is why a four-iteration loop can build four adders, and why a loop whose bound is not known at elaboration cannot be synthesised at all.

This is the most common conceptual error in the topic. In software, a loop saves memory and costs time. In hardware, a loop saves typing and costs area: the iterations become parallel or chained logic that all exists at once.

The four loop forms

Loop statements in Verilog-2001
FormSemanticsSynthesis
for (i = 0; i < N; i = i + 1)Initialise, test, execute, increment, repeat.Yes, when N is constant and the body is synthesizable.
while (cond)Test before each iteration; may run zero times.Not in general: the trip count is not known at elaboration.
repeat (N)Execute the body exactly N times.Rarely; fine in a testbench.
foreverExecute the body endlessly until $finish or disable.No. Used for clock generators and monitors.

forever is the explicit form of what an always block already does. always #5 clk = ~clk; is a forever loop with a delay. Writing forever #5 clk = ~clk; inside an initial block is also legal and equally simulation-only.

What a for loop becomes

Two patterns account for almost all synthesizable for loops:

  • Accumulation. count = count + d[i] over a fixed range builds a chain of adders: the result of iteration 0 feeds iteration 1, and so on. The loop describes a reduction tree, and the tool may balance it.
  • Bit mapping. q[i] = d[7 - i] over a fixed range builds eight wires, each crossing from one input bit to one output bit. The loop is pure wiring, not arithmetic.

Either way, the loop variable must not be a signal that exists in hardware. It is typically an integer, which is a 32-bit signed variable used only during elaboration and simulation. A loop bound must be a constant expression so the tool can decide how many copies to build.

For replicating instances rather than statements, Verilog-2001 provides generate and genvar. A for loop inside a generate block elaborates several module instances with distinct names; a for loop inside an always block elaborates several statements in one procedural block. Both unroll, but only the generate form can create instances.

Line by line

  • integer i; declares the loop variable inside the module. It is shared by every activation of the block, which is acceptable because the block is combinational and executes to completion each time.
  • count = 3'd0; initialises the accumulator before the loop. Without this, the first iteration would add to whatever count held, which is x after power-up and a latch in hardware.
  • for (i = 0; i < 4; i = i + 1) count = count + d[i]; adds each input bit. The body is a single statement, so no begin/end is needed.
  • count = count + d[i]; mixes a three-bit value with a one-bit value. The one-bit operand is zero-extended, and the result is truncated to three bits, which is enough for a maximum of 4.
  • q[i] = d[7 - i]; maps input bit 7 to output bit 0, input bit 6 to output bit 1, and so on. Every output bit is assigned, so there is no latch.
  • Both loops have constant bounds (4 and 8), so synthesis can unroll them fully.

Zero-iteration and infinite loops

A for loop whose condition is false at entry executes zero times. That is legal and sometimes useful, but it means the body's assignments never happen — another route to an inferred latch in a combinational block. A while loop with a condition that never becomes false hangs the simulation at the current time, exactly like an always block without a timing control.

Loops inside a clocked block add a further constraint: if the loop has a fixed trip count, the logic it describes must settle within one clock period. A loop that performs a long computation in one cycle is a large combinational path, not a fast loop. Iterative algorithms in hardware are usually written as a state machine that performs one iteration per clock, which is a structural decision, not a loop.

Common mistakes

  • Expecting a loop to take time. A synthesizable for loop unrolls; all iterations exist in parallel or in a chain.
  • Using a non-constant bound in RTL. If the tool cannot count the iterations at elaboration, it cannot build the hardware.
  • Forgetting to initialise an accumulator. The first iteration adds to an unknown value and synthesis infers storage.
  • Declaring the loop variable as a reg and using it as a signal. The loop variable is elaboration machinery; use an integer and do not read it elsewhere.
  • Using while or forever in synthesizable RTL. The trip count is unknown; the tool cannot build a fixed structure.
  • Writing a loop that does not assign every output bit. The unassigned bits infer latches, exactly as in an incomplete if.
  • Confusing procedural loops with generate loops. Only generate can replicate module instances.

Revision points

  • Synthesizable loops unroll into replicated or chained hardware; they do not iterate over time.
  • for with a constant bound is the standard synthesizable loop; while, repeat and forever are mainly testbench constructs.
  • An accumulator needs an initial value, or the loop infers storage.
  • Use generate with genvar to replicate instances, not a procedural for.
  • Every output bit must be assigned on every path, including inside loops.
