A module is a hardware boundary

Every Verilog design is built from modules. A module has an interface — its ports — and a body that describes what sits behind that interface. Anything outside the module can only touch the ports. That boundary is what makes hierarchy, reuse and independent verification possible.

A module is not a function and it is not a class. It is a hardware component with a fixed interface. Each time you instantiate it, you create another copy of the hardware, with its own internal state and its own wires. Two instances of the same module are two different pieces of silicon that happen to share a definition.

Ports: direction, width and type

Verilog-2001 allows the port list to carry the full declaration, which keeps the interface in one place:

ANSI-style port list
module block (
    input  wire       clk,
    input  wire [7:0] data,
    output wire [7:0] result,
    output reg        valid
);
  • input is driven from outside the module. Inside, an input must not be assigned.
  • output is driven by the module. Outside, it must connect to a net.
  • inout is bidirectional and requires tri-state behaviour and careful bus arbitration. Do not use it as a shortcut for a signal that only travels one way.
  • wire suits outputs driven by assign or by an instance. reg is required when the output is assigned inside an always block. The choice is about how the signal is driven, not about whether a physical register exists.

Widths belong in the declaration. A port declared [7:0] data is eight bits wide and every connection to it should be eight bits wide. Verilog will quietly truncate or zero-extend a mismatched connection at elaboration, which is one of the easiest ways to lose a bit without an error message.

Instances and connections

An instance places one copy of a module inside another module:

Named and positional connection
and2 u_and (.a(a), .b(b), .y(y_and));   // named
and2 u_or  (a, b, y_or);                // positional

Named connections are the professional default. They state the mapping explicitly, survive a reordering of the module's port list, and make a missing port visible during review. Positional connections are compact but fragile: insert one port in the definition and every positional instance in the project silently shifts by one.

A port may be left unconnected by omitting it from a named list, or by writing an empty connection .port(). An unconnected input floats to z, which usually propagates as x. That is acceptable for a deliberately unused output, rarely acceptable for an unused input.

Rules worth memorising

  • A module definition is a template; an instance is a copy of the hardware.
  • Instance names are unique within the parent scope. Hierarchical paths such as dut.u_and identify one specific copy.
  • Port directions are enforced by the language: an input cannot be assigned inside the module, and an output cannot be read as if it were an input unless it is also declared inout (which changes the electrical meaning).
  • Widths are not enforced. Connect equal widths deliberately, or use an explicit slice to show the intended truncation.
  • Module definition order in a file does not matter, provided every module is compiled before elaboration.

Common mistakes

  • Connecting an instance output to a reg. The output drives a net. Declare a wire in the parent and observe it there.
  • Mixing named and positional connections in one instance. Verilog-2001 does not allow the two styles to be combined in the same port list. Choose one.
  • Leaving an input unconnected. It floats to z, and the leaf's outputs usually become x. The design may compile without complaint.
  • Reusing an instance name. Two instances with the same name in one scope are an elaboration error.
  • Assuming a port is a copy. A port is a connection. Driving the same net from two outputs creates contention, not a merge.
  • Changing a port list without checking positional instances. Named connections make this a non-event; positional ones turn it into a silent bug.

Revision points

  • A module is an interface plus a body; an instance is one copy of that module inside a parent.
  • Directions: input is driven from outside, output from inside, inout is bidirectional and needs tri-state discipline.
  • Use named port connections, and keep widths equal on both sides.
  • Hierarchy is created by instantiation, not by textual nesting.
  • Unconnected inputs float; unconnected outputs are usually harmless.
