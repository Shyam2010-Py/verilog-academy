Grouping statements changes when they run

A procedural block contains statements, and the language needs a way to group them. begin/end groups statements that run one after another. fork/join groups statements that run at the same time. The keywords look like block delimiters, but they encode a scheduling decision that is visible in the simulation output.

This topic is short but easy to get wrong. Sequential blocks are the everyday case; parallel blocks are a testbench tool that is rarely synthesizable and must be used deliberately.

begin/end: statements in order

Inside a begin/end block, each statement starts after the previous one finishes. If a statement contains a timing control, the whole block waits. That is why the example's sequential demonstration prints at 0, 2, 4 and 6 ns.

Sequential timing
begin
    #2 a = 1'b1;   // t = 2
    #2 b = 1'b1;   // t = 4
    #2 c = 1'b1;   // t = 6
end

Sequential blocks can be named: begin : sequential_demo ... end. A named block creates a scope, which is useful for local declarations and for disable. The name also appears in hierarchical paths and in error messages, so naming a large testbench block is good practice.

fork/join: statements together

fork/join starts every branch at the same simulation time and waits for all of them to finish before continuing past join.

Parallel timing
fork
    begin #4 a = 1'b0; end   // t = 4 relative
    begin #6 b = 1'b0; end   // t = 6 relative
    begin #8 c = 1'b0; end   // t = 8 relative
join
// resumes at t = 8 relative, when the slowest branch finishes

The delays are measured from the moment the fork starts, not from the previous branch. Branch 2 does not wait for branch 1. The block after join runs only when every branch has completed, so its time is the time of the slowest branch.

Verilog-2001 has only join. SystemVerilog adds join_any (resume when one branch finishes) and join_none (start the branches and continue immediately). Those are outside this course's language subset and toolchain.

Line by line

  • initial begin : sequential_demo names the block. The name is optional but useful in a testbench.
  • #2 a = 1'b1; waits 2 ns then assigns. The next $display prints at 2 ns.
  • The next #2 is relative to the current time, not to time zero, so b is set at 4 ns and c at 6 ns. Each delay accumulates.
  • The second initial block starts at time zero too, but its first statement is #12;, so its fork begins at 12 ns.
  • fork ... join starts all three branches at 12 ns. Their delays are 4, 6 and 8, so the branches finish at 16, 18 and 20 ns.
  • The $display after join runs at 20 ns, when the last branch finishes, and shows all three values cleared.
  • Both initial blocks run concurrently. The sequential demo finishes at 6 ns without affecting the parallel demo, which is still waiting for its delay.

The actual run

{{OUTPUT:examples/verilog/sequential-parallel-blocks/expected.txt}}

The first four lines increase by 2 ns each: 0, 2, 4, 6. That is the sequential schedule, with every delay measured from the previous statement.

The remaining lines start at 12 ns and then show 16, 18 and 20 ns. Those are 4, 6 and 8 ns after the fork, running concurrently. The final line at 20 ns proves that join waits for the slowest branch: a and b were already cleared, and c has just been cleared.

If the same three delays were written in a begin/end block, the times would be 4, 10 and 18 ns, because each delay would start after the previous one completed. The difference is entirely in the block keyword.

Parallel blocks and synthesis

fork/join is a simulation construct. Synthesis tools generally reject it, or accept only a restricted form with no timing controls, which is of little practical use. The reasons are structural: parallel branches imply concurrent processes with independent timing, and there is no general hardware mapping for that without a scheduler.

Hardware concurrency is expressed by separate always blocks or by instantiating several modules. Those are concurrent by construction, not by a fork. When you see fork in a design file rather than a testbench, treat it as a warning sign and check whether the file is really a testbench or a behavioural model.

Named blocks and disable have a legitimate testbench use: a watchdog can disable a named stimulus block that has hung. That is a verification technique, not a hardware description.

Common mistakes

  • Assuming fork branches are sequential. They start together. Delays are relative to the fork, not to the previous branch.
  • Assuming join returns after the first branch. It waits for all branches. join_any is SystemVerilog.
  • Putting fork in synthesizable RTL. It has no general hardware mapping.
  • Forgetting that separate initial blocks already run concurrently. A fork inside one block is not needed to get concurrency with another block.
  • Relying on the order of two blocks that resume at the same time. The language does not define it.
  • Naming a block and then declaring a signal with the same name. The block name introduces a scope; collisions produce confusing errors.

Revision points

  • begin/end runs statements in order; each timing control delays the rest of the block.
  • fork/join starts branches together and resumes when the slowest finishes.
  • Delays inside a fork are all measured from the fork, not chained.
  • Verilog-2001 has only join; join_any and join_none are SystemVerilog.
  • Parallel blocks are testbench constructs; hardware concurrency comes from separate always blocks and instances.
