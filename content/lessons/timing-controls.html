Procedural code needs to know when

A procedural block does not run on its own. Something has to tell it when to execute: a delay that elapses, an event that occurs, or a condition that becomes true. Those three mechanisms are Verilog's timing controls, and they are the difference between a script and a hardware model.

This topic covers the controls themselves. Their role in synthesis is just as important: delays are ignored, edges become clock and reset pins, and level waits are generally not synthesizable at all. A control that is perfect for a testbench can make an RTL block unbuildable.

The three controls

Timing controls in Verilog-2001
FormMeaningTypical use
#10;Delay: wait 10 time units.Testbench stimulus, clock generation.
@(posedge clk);Event: wait for a rising edge on clk.Clocked logic, edge-aligned sampling.
@(a or b);Event: wait for any change on a or b.Pre-2001 combinational sensitivity; still used for mixed lists.
wait (state == 2);Level: block until the expression is true.Testbench synchronisation; not synthesizable.
@(posedge clk or negedge rst_n);Event list with two sources.Asynchronous reset register.

These controls can appear at the head of a statement or alone as a statement. @(posedge clk); on its own simply waits. @(posedge clk) q <= d; performs an intra-statement event control: wait for the edge, then execute the assignment.

Intra-assignment delays

A delay can also sit inside an assignment:

Two positions, two meanings
#5 q = d;      // wait 5, then evaluate d and assign immediately
q = #5 d;      // evaluate d now, assign 5 time units later
q <= #5 d;     // evaluate d now, schedule the update 5 later

The difference matters when d can change during the delay. In the first form, d is read after the wait, so the assignment sees the later value. In the second, d is captured first and the old value is written later. The third form is the non-blocking variant, used in cell models to represent output delay without blocking the block.

All three are simulation constructs. Synthesis ignores them, often with a warning.

Line by line

  • always #5 clk = ~clk; generates a 10 ns period clock: rising edges at 5, 15, 25, 35 and so on.
  • always @(posedge clk) with if (start && state < 2'd3) is a gated counter. It stops at 3 rather than wrapping, because the comparison prevents further increments.
  • #7 start = 1'b1; waits 7 ns from time zero, then raises start. There is no clock edge at 7 ns, so the counter does not move yet.
  • @(posedge clk); blocks the initial block until the next rising edge. The first one after 7 ns is at 15 ns, so the message prints at 15 ns.
  • wait (state == 2'd2); blocks until the condition is true. The counter reaches 1 at 15 ns and 2 at 25 ns, so the message prints at 25 ns, immediately when the state updates. A level wait is sensitive to a condition, not to an edge.
  • #3 $display(...) waits three more time units and prints at 28 ns.

Each line is evidence for one control:

  • 7000: the delay ended at 7 ns and the statement executed.
  • 15000: the event control resumed exactly on the first rising edge after the delay. Not at 7 ns, not at 10 ns.
  • 25000: the wait resumed in the same time step in which state became 2, not at the following edge.
  • 28000: the final delay added three time units to the wait's completion.

The printed values are in picoseconds because %0t uses the simulation precision. Seven nanoseconds is 7000 ps.

What survives synthesis

Timing controls versus synthesis
ControlSynthesis result
@(posedge clk)Clock input of a flip-flop.
@(posedge clk or negedge rst_n)Flip-flop with asynchronous reset.
@*Combinational logic with inferred sensitivity.
#delayIgnored, or rejected. Timing comes from the library.
wait (level)Not synthesizable as written; usually a latch or a protocol handshake in disguise.
@(a or b) on data signalsCombinational logic; equivalent to @* if the list is complete.

The distinction is not academic. A design that uses wait to sequence operations will simulate exactly as intended and then fail synthesis with an obscure message. If a behavioural model needs sequencing, use a clock and a state machine, not a level wait.

Timing controls and races

Timing controls do not remove races; they move them. Two blocks that both wait for posedge clk resume in an order the language does not define. If one samples a value that the other updates at the same edge, the result depends on scheduling. The standard defences are non-blocking assignment in clocked blocks, sampling on the opposite edge in a testbench, or sampling after a small delay.

Adding #1 to hide a race is a common but weak fix: it changes the timing rather than the ordering guarantee, and it can hide a real design bug. Use it only in a testbench where the intent is explicit.

Common mistakes

  • Confusing @ with wait. An event control resumes on a transition; a wait resumes when a condition is true, which may be immediately.
  • Using # in synthesizable RTL. It is ignored, so the hardware has no delay, and the simulation is misleading.
  • Forgetting that a delay is in timescale units. #5 is 5 ns only if the active timescale says so.
  • Waiting for an edge that already happened. @(posedge clk) waits for the next edge; it does not test the current level.
  • Using wait in a design that must synthesise. It has no hardware equivalent as written.
  • Relying on the order of two blocks resuming at the same edge. The order is undefined; use non-blocking assignment or opposite-edge sampling.

Revision points

  • # is a delay, @ is an event control, wait is a level control.
  • @(posedge clk) resumes on the next rising edge, never on a previous one.
  • An intra-assignment delay changes when a value is read or written; the position of # matters.
  • Edge controls become clock and reset pins in synthesis; delays are ignored; level waits are not synthesizable.
  • Timing controls do not define the order between blocks that resume at the same time.
