When the built-in primitives are not enough

Verilog's gate primitives cover AND, OR, XOR and their complements, plus tri-state buffers. A user-defined primitive (UDP) lets you add a gate whose behaviour is given directly as a truth table, without writing a module or an expression. It is the lowest-level way to describe a component in the language.

UDPs exist for two reasons. First, some components are naturally tabular — a multiplexer, a latch, a custom cell from a library — and a table is clearer than an equation. Second, a technology library may need to describe a cell exactly as the vendor specifies it, including its behaviour on unknown inputs. For everyday RTL, UDPs are unnecessary; for cell modelling and teaching, they are the cleanest possible description.

Primitive syntax

UDP skeleton
primitive name (out, in1, in2);
    output out;
    input  in1, in2;
    table
        // in1 in2 : out
           0   0  : 0;
           0   1  : 1;
    endtable
endprimitive
  • The output comes first in the port list, as with gate primitives.
  • A UDP has exactly one output. That is a language restriction, not a style choice.
  • The body is a table, with one row per input combination. Every column before the colon is an input; the column after the colon is the output.
  • The table must be complete for the input combinations the designer cares about. A missing row produces x, which is the language's way of saying "not specified".
  • UDPs contain no expressions, no assignments and no timing controls. The table is the behaviour.

Table symbols

Symbols used in UDP tables
SymbolMeaning
0, 1, xA specific logic value.
?Don't care: matches 0, 1, x or z.
bEither 0 or 1, but not x or z.
-No change: the output keeps its previous value. Sequential UDPs only.
(01)A rising edge on that input.
(10)A falling edge.
(??)Any change on that input.

The distinction between a combinational UDP and a sequential UDP is the presence of the reg declaration and the extra state column. A sequential UDP row has the form inputs : current_state : next_state; a combinational UDP row has the form inputs : output.

Line by line

  • primitive mux2_udp (out, sel, a, b); declares a primitive with one output and three inputs. The order matters: the first port is always the output.
  • 0 0 ? : 0; means "when sel is 0, a is 0 and b is anything, the output is 0". The ? in the b column is what makes this a multiplexer rather than a full truth table.
  • 1 ? 0 : 0; is the mirror case: sel is 1 and b is 0, regardless of a.
  • The four rows together cover all eight input combinations. There is no default row, because every combination is specified.
  • primitive dlatch_udp (q, en, d); declares the sequential primitive. output q; reg q; is required: the output must be a variable because it stores a value.
  • 1 0 : ? : 0; means "enable high, data 0, whatever the current state, next state is 0". The latch is transparent.
  • 0 ? : ? : -; means "enable low, any data, any current state, next state is the current state". The - is the hold.
  • The current-state column contains ? in every row, meaning the next state does not depend on it. That is correct for a transparent latch: when enabled it follows the data, and when disabled it holds, so the current state never changes the decision.

The multiplexer rows follow the definition: with sel = 0 the output equals a, and with sel = 1 it equals b. Because a and b are complementary in some rows and equal in others, the table checks every path through the primitive, not just the easy ones.

The latch rows show the three states of a transparent latch:

  • en=1 d=1 -> q=1: enabled, so the output follows the data.
  • en=0 d=0 -> q=1 (held): disabled, so the new data is ignored and the previous value is held. The - row did its job.
  • en=1 d=0 -> q=0: enabled again, so the output follows the new data.

This is the same behaviour as the incomplete always @* block from the previous topic, but here it is intentional and expressed as a table.

Simulator limitation, stated honestly

The installed simulator, Icarus Verilog 13.0, compiles an edge-sensitive UDP but does not evaluate its edge rows: the output remains x under every language-generation flag we tried. That is why this file is presented as a language reference and is not part of the verified example set. The level-sensitive latch above is simulated and its output is real.

The syntax is still worth learning, because vendor cell libraries use edge-sensitive UDPs for exactly this purpose. Do not conclude from one simulator's limitation that the construct is invalid; check the tool's documentation before relying on it.

Limits of user-defined primitives

  • One output per primitive, and the output must be first in the port list.
  • No timing controls, no expressions and no module instances inside the table.
  • A table row covers one combination (or one edge), so a wide primitive needs many rows. A 4:1 multiplexer with three data bits would need many pages.
  • Some synthesis tools support only combinational UDPs, or none at all. UDPs are primarily a simulation and library-modelling feature.
  • The table is not checked against your intent. A typo in a row produces a primitive that simulates exactly as written and is wrong.

For design work, a module with an assign or a case statement is usually the better choice: it is readable, parameterisable and portable. Reach for a UDP when the tabular form is the clearest possible statement of the behaviour, or when a library demands it.

Common mistakes

  • Putting the output last. As with gate primitives, the output is the first port. A reversed list compiles into a primitive with the wrong direction.
  • Forgetting reg on a sequential output. A sequential UDP stores state, so its output must be a variable.
  • Leaving table rows out. Unspecified combinations produce x, which may look like a simulator bug.
  • Using - in a combinational UDP. The hold symbol is only meaningful when the primitive has state.
  • Assuming ? means "don't care about the output". It is a wildcard on an input or on the current state; the output column still has to say what happens.
  • Writing a large function as a UDP table. The table grows exponentially with input width; use a module instead.
  • Assuming every simulator handles edge-sensitive UDPs. Verify with your tool before depending on one.

Revision points

  • A UDP defines a primitive by a truth table, with the output first and exactly one output.
  • Combinational rows are inputs : output; sequential rows add a current-state column and use - to hold.
  • A sequential UDP's output must be declared reg.
  • ? is a don't-care, b is 0 or 1 only, and (01)/(10) are edges.
  • UDPs are for tabular cells and library models; modules are better for general design work.
