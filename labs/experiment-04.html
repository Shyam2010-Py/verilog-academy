EC-410 · Experiment 04

4-bit ripple carry · 512 vectors

Laboratory overview EC-405 theory

Aim and scope

Build a four-bit parallel adder by connecting four full-adder instances in a ripple-carry chain, expose the unsigned carry-out and the signed overflow flag, and verify all 512 input combinations.

This experiment moves from a single one-bit stage to a working multi-bit datapath. The four full adders are structural instances, not a behavioural + operator, so the carry path is visible in the source. That visibility is the point: each stage's carry-out becomes the next stage's carry-in, and the last two carries also determine signed overflow.

The design has two distinct carry-related outputs. cout is the carry out of the most significant bit and indicates unsigned overflow when the operands are treated as unsigned. overflow is the XOR of the carry into and the carry out of the most significant bit and indicates signed overflow. They answer different questions and must not be conflated.

Learning objectives

  • Instantiate a module four times with named port connections.
  • Route a carry chain from the least significant to the most significant stage.
  • Distinguish unsigned carry-out from signed overflow.
  • Compute overflow = c4 ^ c3 and explain why the XOR works.
  • Verify all 512 combinations of two four-bit operands and a carry-in.
  • Recognise the propagation-delay limitation of a ripple-carry structure.

Theory and working principle

A four-bit adder adds a[3:0], b[3:0] and a carry-in. Bit 0 has no incoming carry from a less significant stage, so it receives cin. Each subsequent bit receives the carry produced by the bit below it. The result is a five-bit unsigned value {cout, sum}.

Each stage is a full adder with sum = a ^ b ^ carry_in and carry_out = (a & b) | (carry_in & (a ^ b)). In a ripple-carry adder the carry propagates through the stages one after another. That is simple and area-efficient, but the worst-case delay grows with the number of bits because the most significant sum cannot settle until every carry below it has settled.

The carry out of the final stage, c4, is the unsigned carry-out. If the operands are unsigned four-bit numbers, c4 = 1 means the exact sum is 16 or more and does not fit in four bits. If the operands are signed two's-complement numbers, the range is −8 to +7. Signed overflow occurs when the exact result falls outside that range. It can be detected by comparing the carry into the sign bit with the carry out of the sign bit: overflow = c4 ^ c3. The two carries differ exactly when the sign of the result is wrong.

This is why 1000 + 1000 sets both cout and overflow, while 1111 + 0001 sets cout but not overflow. Unsigned 15 + 1 = 16 overflows four unsigned bits; signed −1 + 1 = 0 is perfectly valid and does not overflow.

Logic diagram

Four full-adder blocks are chained from bit 0 to bit 3. The carry wire between bit 2 and bit 3 is c3; the carry out of bit 3 is c4. The overflow XOR taps those two nodes, not cout and cin.

The first row of interest is 0100 + 0100. Unsigned 4 + 4 = 8, which fits in five bits but not in the signed range −8…+7, so cout = 0 and overflow = 1. Boolean equations

Carry bit ic[i+1] = (a[i] & b[i]) | (c[i] & (a[i] ^ b[i]))
Carry-inc[0] = cin
Carry-outcout = c[4]
Overflowoverflow = c[4] ^ c[3]

In the Verilog source, the wire carry[0] is c[1] and carry[3] is c[4]. The expression carry[3] ^ carry[2] is therefore c[4] ^ c[3]. The names differ, but the nodes are the same.

Verilog design code

The file defines the full-adder stage first and then instantiates it four times. Named port association makes each carry connection explicit and prevents a silent bit-order mistake.

design.v 
`default_nettype none
`timescale 1ns / 1ps

// EC-410 Experiment 04 - four-bit ripple-carry parallel adder.
// A single full-adder module is instantiated four times; carry[4] is the
// carry out of the most significant stage and also the unsigned carry-out.

module full_adder (
    input  wire a,
    input  wire b,
    input  wire cin,
    output wire sum,
    output wire carry
);

    assign sum   = a ^ b ^ cin;
    assign carry = (a & b) | (cin & (a ^ b));

endmodule


module parallel_adder_4 (
    input  wire [3:0] a,
    input  wire [3:0] b,
    input  wire       cin,
    output wire [3:0] sum,
    output wire       cout,
    output wire       overflow
);

    wire [3:0] carry;   // carry[0] is the carry out of bit 0

    full_adder fa0 (
        .a(a[0]), .b(b[0]), .cin(cin),
        .sum(sum[0]), .carry(carry[0])
    );

    full_adder fa1 (
        .a(a[1]), .b(b[1]), .cin(carry[0]),
        .sum(sum[1]), .carry(carry[1])
    );

    full_adder fa2 (
        .a(a[2]), .b(b[2]), .cin(carry[1]),
        .sum(sum[2]), .carry(carry[2])
    );

    full_adder fa3 (
        .a(a[3]), .b(b[3]), .cin(carry[2]),
        .sum(sum[3]), .carry(carry[3])
    );

    assign cout     = carry[3];
    assign overflow = carry[3] ^ carry[2];

endmodule

`default_nettype wire

Testbench

The testbench first prints nine selected cases, then sweeps ai from 0 to 15, bi from 0 to 15 and ci from 0 to 1. Overflow is predicted from the exact signed sum, not from the design's own carry bits, so the two computations are independent.

tb.v 
`default_nettype none
`timescale 1ns / 1ps

module parallel_adder_4_tb;
    reg  [3:0] a;
    reg  [3:0] b;
    reg        cin;
    wire [3:0] sum;
    wire       cout;
    wire       overflow;

    integer ai, bi, ci;
    integer errors;
    integer checks;
    integer exact_signed;
    reg [4:0] expected_sum;
    reg expected_overflow;

    parallel_adder_4 dut (
        .a(a), .b(b), .cin(cin),
        .sum(sum), .cout(cout), .overflow(overflow)
    );

    task show_case;
        input [3:0] ta;
        input [3:0] tb;
        input       tc;
        begin
            a = ta; b = tb; cin = tc;
            #1;
            exact_signed = $signed({ta[3], ta}) + $signed({tb[3], tb}) + $signed({1'b0, tc});
            expected_sum = ta + tb + tc;
            expected_overflow = (exact_signed < -8) || (exact_signed > 7);
            $display(" %b + %b + %b = %b  cout=%b overflow=%b",
                     ta, tb, tc, {cout, sum}, cout, overflow);
        end
    endtask

    initial begin
        errors = 0;
        checks = 0;

        $display("SELECTED CASES");
        $display("a     b    cin | sum  cout ovf");
        $display("----------------+--------------");
        show_case(4'b0000, 4'b0000, 1'b0);
        show_case(4'b0011, 4'b0100, 1'b0);
        show_case(4'b0100, 4'b0100, 1'b0);
        show_case(4'b0111, 4'b0001, 1'b0);
        show_case(4'b1000, 4'b0111, 1'b0);
        show_case(4'b1111, 4'b0001, 1'b0);
        show_case(4'b1001, 4'b0111, 1'b0);
        show_case(4'b1000, 4'b1000, 1'b0);
        show_case(4'b1010, 4'b0101, 1'b1);

        $display("");
        $display("EXHAUSTIVE CHECK");
        for (ai = 0; ai < 16; ai = ai + 1) begin
            for (bi = 0; bi < 16; bi = bi + 1) begin
                for (ci = 0; ci < 2; ci = ci + 1) begin
                    a = ai[3:0];
                    b = bi[3:0];
                    cin = ci[0];
                    #1;
                    exact_signed = $signed({a[3], a}) + $signed({b[3], b}) + $signed({1'b0, cin});
                    expected_sum = a + b + cin;
                    expected_overflow = (exact_signed < -8) || (exact_signed > 7);
                    checks = checks + 1;

                    if ({cout, sum} !== expected_sum || overflow !== expected_overflow) begin
                        errors = errors + 1;
                        if (errors <= 3) begin
                            $display("MISMATCH a=%b b=%b cin=%b got=%b ovf=%b expected=%b ovf=%b",
                                     a, b, cin, {cout, sum}, overflow, expected_sum, expected_overflow);
                        end
                    end
                end
            end
        end

        $display("checked %0d combinations, mismatches = %0d", checks, errors);
        $finish;
    end
endmodule

Line-by-line explanation

Design

  • full_adder is a one-bit stage. Its sum and carry equations are the same as Experiment 02, but written in the compact expanded form.
  • parallel_adder_4 declares two four-bit operands, a carry-in, a four-bit sum and two flags.
  • wire [3:0] carry; holds the four inter-stage carries. carry[0] is produced by bit 0 and consumed by bit 1.
  • fa0 receives cin and produces sum[0] and carry[0].
  • fa1, fa2 and fa3 each take the previous stage's carry. This chain is the ripple.
  • assign cout = carry[3]; exposes the final carry as an output.
  • assign overflow = carry[3] ^ carry[2]; compares the carry into and out of the sign stage.

Testbench

  • expected_sum is five bits so it can hold 16 or more. A four-bit expected value would silently wrap.
  • exact_signed is an integer holding the signed arithmetic result.
  • $signed({ta[3], ta}) sign-extends a four-bit operand to five bits before conversion, so 1000 is treated as −8 rather than +8.
  • expected_overflow = (exact_signed < -8) || (exact_signed > 7); is the definition of signed overflow for a four-bit result.
  • {cout, sum} concatenates the outputs into the five-bit result for comparison with expected_sum.
  • The triple loop performs 16 × 16 × 2 = 512 checks and prints only the first three failures, which keeps a failing transcript readable.

Waveform and timing

The first nine vectors occupy 0–9 ns. The exhaustive sweep applies one vector per nanosecond from 9 ns to 521 ns. In a real ripple-carry adder the carry would arrive later at each stage; this zero-delay model shows only the settled logic values.

If you add delays inside the full-adder module, a waveform would show each sum[i] settling after carry[i]. That is the ripple effect the name describes. The functional transcript would not change, because the testbench waits before sampling.

Result

All 512 combinations produced the correct sum, carry and overflow.

The exhaustive sweep checked 512 input combinations and reported 0 mismatches. The selected cases demonstrate that cout and overflow are independent flags: each can be 1 while the other is 0.

This is complete functional verification of a four-bit adder with carry-in. It does not measure worst-case delay, and it does not verify a gate-level netlist after synthesis.

Common mistakes and troubleshooting

Using cin for overflow

overflow = cout ^ cin is wrong for a multi-bit adder. The correct comparison is the carry into and out of the sign bit, c4 ^ c3.

Treating cout as signed overflow

1111 + 0001 sets cout but is a valid signed operation. Unsigned carry and signed overflow answer different questions.

Connecting the carry chain backwards

fa1 must take carry[0], not carry[1]. A reversed connection can still compile, so only the exhaustive test exposes it.

Declaring the expected sum as four bits

reg [3:0] expected_sum cannot represent 16. Use five bits for a four-bit addition with carry-out.

Sign-extending incorrectly

$signed(a) on a four-bit value does not widen it to five bits. Concatenate the sign bit first: $signed({a[3], a}).

Forgetting the testbench delay

Without a settling delay, the comparison may read the previous vector. Each vector is held for 1 ns in this testbench.

Viva questions

  1. Why is the carry out of bit 3 not the same as signed overflow?
  2. For a = 1000 and b = 1000, give the sum, cout and overflow.
  3. How many full adders are needed for a 16-bit ripple-carry adder?
  4. What is the worst-case carry propagation path in this circuit?
  5. How would a carry-look-ahead adder reduce that path?
  6. Why does the testbench use 512 vectors rather than a sample of cases?
  7. What does {cout, sum} represent as an unsigned integer?

Revision points

  • A four-bit ripple-carry adder is four full adders with the carry chained.
  • cout = c4 is unsigned carry-out; overflow = c4 ^ c3 is signed overflow.
  • Unsigned overflow and signed overflow are independent; either can occur without the other.
  • Five bits are needed for the full result of a four-bit addition.
  • 512 vectors exhaust two four-bit operands plus one carry-in.
  • Ripple carry is simple but slow; the critical path passes through every stage.
