Gate Level and Data Flow Modelling

Unit overview

One ALU, three descriptions

An arithmetic logic unit is the block that makes a processor a processor: it takes two operands and an operation code and produces a result. The interesting lesson is not the ALU itself, but the fact that the same ALU can be written as gates, as equations, or as a procedural case statement — and that synthesis must produce equivalent hardware from all three.

This topic closes Unit 2 by comparing the modelling styles you have learned. It is also the first place where a design is verified by equivalence rather than by a handful of examples: two independent descriptions are driven with every possible input and compared.

Specify before you model

A four-bit ALU with a two-bit operation code has a small, complete specification:

Operation encoding used in the example
opFunctionExpression
00Bitwise ANDa & b
01Bitwise ORa | b
10Additiona + b, low four bits
11Subtractiona - b, low four bits

Two consequences follow immediately. First, addition and subtraction produce four-bit results here, so the carry out and the borrow are discarded; a real ALU would expose them as status flags. Second, the operation code is fully decoded, so there is no "undefined" encoding — but a defensive description still needs a default branch for the simulator's x and z states.

The three modelling styles

Gate level

Primitive gates and instances wired into an adder and a multiplexer tree. It mirrors a netlist and makes the gate count visible, but it is slow to write and hard to change.

Dataflow

Continuous assignments with nested conditional operators or arithmetic. It reads like a datapath equation and maps directly onto multiplexers and an adder.

Behavioural

An always @* block with a case statement. It reads like the specification table and is the easiest to extend with new operations.

All three describe the same combinational function, and all three are synthesizable. The difference is in how directly the source expresses intent. For an ALU with four operations, the behavioural case wins on readability; for a leaf adder inside it, dataflow is compact; for a library cell, gate level is the only option.

The executed example contains the dataflow and behavioural descriptions and proves them equivalent. The gate-level description is what synthesis builds from either of them — a multiplexer tree selecting between an AND plane, an OR plane, an adder and a subtractor. Writing that netlist by hand would add pages of code and no information.

Two descriptions, one exhaustive check

The design file contains both modules. The testbench instantiates both, drives them with identical inputs, and compares the outputs with the case-equality operator.

design.v 
`default_nettype none
// Two descriptions of the same 4-bit ALU.
module alu4_dataflow (
    input  wire [3:0] a,
    input  wire [3:0] b,
    input  wire [1:0] op,
    output wire [3:0] y
);
    assign y = (op == 2'b00) ? (a & b)
             : (op == 2'b01) ? (a | b)
             : (op == 2'b10) ? (a + b)
             :                 (a - b);
endmodule

module alu4_behavioural (
    input  wire [3:0] a,
    input  wire [3:0] b,
    input  wire [1:0] op,
    output reg  [3:0] y
);
    always @* begin
        case (op)
            2'b00:   y = a & b;
            2'b01:   y = a | b;
            2'b10:   y = a + b;
            2'b11:   y = a - b;
            default: y = 4'b0000;
        endcase
    end
endmodule
`default_nettype wire

Line by line: the design

  • alu4_dataflow has a wire output because it is driven by assign. alu4_behavioural has an output reg because the output is assigned inside an always block. The port type follows the driver, not the intended hardware.
  • assign y = (op == 2'b00) ? (a & b) : ... is a chain of 2:1 multiplexers. The conditional operator is right-associative, so the nesting reads top to bottom: test 00, then 01, then 10, and fall through to subtraction.
  • The final branch needs no comparison. If op is not 00, 01 or 10, it must be 11 for a two-bit value — or x/z, in which case the subtraction result is also unknown. That is acceptable for this specification but should be a conscious choice.
  • case (op) tests the four encodings in order and assigns y on every branch. default: y = 4'b0000; covers the x/z case and guarantees that y is assigned on every path.
  • Every branch assigns y, so the block describes pure combinational logic. Remove the default and synthesis may infer a latch to hold the previous value — the classic incomplete-assignment bug from the previous topic.
tb.v 
`default_nettype none
`timescale 1ns / 1ps

module alu_compare_tb;
    reg  [3:0] a;
    reg  [3:0] b;
    reg  [1:0] op;
    wire [3:0] y_flow;
    wire [3:0] y_beh;
    integer ai;
    integer bi;
    integer oi;
    integer checks;
    integer mismatches;

    alu4_dataflow    u_flow (.a(a), .b(b), .op(op), .y(y_flow));
    alu4_behavioural u_beh  (.a(a), .b(b), .op(op), .y(y_beh));

    initial begin
        checks     = 0;
        mismatches = 0;

        // Exhaustive equivalence check over every input combination.
        for (ai = 0; ai < 16; ai = ai + 1) begin
            for (bi = 0; bi < 16; bi = bi + 1) begin
                for (oi = 0; oi < 4; oi = oi + 1) begin
                    a  = ai[3:0];
                    b  = bi[3:0];
                    op = oi[1:0];
                    #1;
                    checks = checks + 1;
                    if (y_flow !== y_beh) begin
                        mismatches = mismatches + 1;
                        $display("MISMATCH a=%b b=%b op=%b dataflow=%b behavioural=%b",
                                 a, b, op, y_flow, y_beh);
                    end
                end
            end
        end
        $display("compared %0d input combinations, mismatches = %0d", checks, mismatches);

        a = 4'b1010;
        b = 4'b0101;
        $display("a=%b (10)  b=%b (5)", a, b);
        $display("op | result | decimal");
        $display("---+--------+--------");
        for (oi = 0; oi < 4; oi = oi + 1) begin
            op = oi[1:0];
            #1;
            $display("%b |  %b  |    %2d", op, y_flow, y_flow);
        end
        $finish;
    end
endmodule
`default_nettype wire

Line by line: the testbench

  • Two instances receive the same a, b and op signals. Only the outputs are separate wires.
  • Three nested for loops cover 16 values of a, 16 of b and 4 values of op — 1024 combinations, which is every possible input.
  • a = ai[3:0]; slices the 32-bit loop counter down to the four bits the port expects. Assigning a = ai; would also work, but the slice documents the width conversion.
  • if (y_flow !== y_beh) uses case inequality, so an x in either output counts as a mismatch instead of being ignored. A comparison that cannot decide is not a pass.
  • checks = checks + 1; counts the compared vectors. Printing the count is part of the evidence: 1024 means the loops really covered the space.
  • The second half prints four representative results for a = 1010 and b = 0101, so the reader can check the arithmetic by hand.

The actual run

Simulator output actual run · Icarus 13.0 
compared 1024 input combinations, mismatches = 0
a=1010 (10)  b=0101 (5)
op | result | decimal
---+--------+--------
00 |  0000  |     0
01 |  1111  |    15
10 |  1111  |    15
11 |  0101  |     5
tb.v:52: $finish called at 1028000 (1ps)

The first line is the important one: 1024 combinations, 0 mismatches. That is a complete proof of equivalence for this input space, not a sample. The remaining rows are a spot check that the functions are the intended ones:

  • 1010 AND 0101 = 0000: no bit position has both inputs set.
  • 1010 OR 0101 = 1111: the operands are complementary, so every bit is covered.
  • 1010 + 0101 = 1111 (10 + 5 = 15), which fits in four bits.
  • 1010 - 0101 = 0101 (10 - 5 = 5).

Ten plus five is exactly 15, so this particular addition does not exercise the carry loss. The exhaustive loop does: it compares every operand pair, including those that overflow, and both descriptions discard the carry in the same way.

Why equivalence checking matters

Comparing two descriptions sounds like academic exercise, but it is the core of real verification:

  • Refactoring: when a block is rewritten for clarity or timing, the old and new versions can be simulated side by side. Equal outputs on exhaustive or constrained-random stimulus give confidence that the rewrite preserved behaviour.
  • Synthesis: formal equivalence checking proves that the gate netlist implements the RTL for all inputs, not just the simulated ones. That is stronger than any testbench and is a standard signoff step.
  • Optimisation: a synthesis tool may restructure logic aggressively. Equivalence checking catches the rare case where an optimisation changes behaviour, for example around x handling.

Note the limit of this example: two descriptions that agree may both be wrong with respect to the specification. Equivalence proves consistency, not correctness. The specification table and the hand-checked rows are what tie the pair to the intended ALU.

Common mistakes

  • Comparing with == in the checker. If either output is x, == returns x, the if does not fire, and the mismatch is silently ignored. Use !==.
  • Leaving a branch unassigned in the case. Synthesis infers a latch. Always assign the output on every path, with a default.
  • Forgetting the carry. A four-bit ALU that adds in four bits silently wraps. If the design needs a carry flag, compute in five bits and expose the extra bit.
  • Treating the two descriptions as equally efficient. Synthesis may map them differently. Equivalence of behaviour does not guarantee identical area or timing.
  • Assuming a passing comparison proves the specification. It proves the two models agree. Check the function against the table separately.
  • Using a behavioural ALU as a synthesizable block without checking the inferred hardware. A large case with arithmetic can infer several adders unless the tool shares them.

Revision points

  • An ALU is a multiplexer over several functions sharing the same operands; the operation code selects the function.
  • Gate-level, dataflow and behavioural descriptions can all be synthesizable; they differ in readability and in how directly they express structure.
  • The conditional operator chain and the case statement describe the same priority multiplexer.
  • Assign every output on every path, or synthesis infers a latch.
  • Exhaustive comparison with !== proves equivalence over the tested space; formal equivalence checking extends that to all inputs and to the netlist.
