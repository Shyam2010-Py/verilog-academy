Gate Level and Data Flow Modelling

Unit overview

A continuous assignment is a permanent connection

Dataflow modelling describes combinational hardware as equations. assign y = (a & b) | c; does not execute once; it declares that the net y is permanently driven by that expression. Whenever an input changes, the simulator re-evaluates the right-hand side and updates the net.

All continuous assignments in a module are concurrent. Their textual order has no meaning. This is the cleanest way to describe arithmetic, selection and routing logic, and it is the level at which many synthesis reports describe the resulting circuit.

Rules of the dataflow style

  • The left-hand side must be a net, not a reg. assign drives a connection.
  • The right-hand side may be any expression of nets, variables and constants. It may include the conditional operator, concatenation and function calls.
  • Every assignment is evaluated whenever any signal on its right-hand side changes. There is no "next statement".
  • Two continuous assignments to the same net create multiple drivers. If they disagree, the net becomes x.
  • A delay on the assignment (assign #5 y = ...) is a simulation model only and is ignored by synthesis.

Dataflow describes combinational logic. It cannot store a value; there is no state in a continuous assignment. If a design needs memory, that memory lives in a procedural block or in an inferred RAM, not in an assign.

The conditional operator is a multiplexer

sel ? a : b is the natural dataflow description of a 2:1 multiplexer. Nesting the operator builds wider multiplexers, but the nesting must be read carefully: the conditional operator is right-associative, so a ? b : c ? d : e means a ? b : (c ? d : e). Parenthesise nested selections so a reader does not have to know that rule.

A 4:1 multiplexer

The example selects one bit from a four-bit input using a two-bit select. The testbench holds the data constant and walks all four select values.

example.v 
`default_nettype none
// Every output is a continuous function of the inputs.
module mux4 (
    input  wire [3:0] d,
    input  wire [1:0] sel,
    output wire       y
);
    assign y = sel[1] ? (sel[0] ? d[3] : d[2])
                      : (sel[0] ? d[1] : d[0]);
endmodule

module mux4_tb;
    reg  [3:0] d;
    reg  [1:0] sel;
    wire       y;
    integer i;

    mux4 dut (.d(d), .sel(sel), .y(y));

    initial begin
        d = 4'b1010;
        $display("d=%b", d);
        $display("sel | y");
        $display("----+--");
        for (i = 0; i < 4; i = i + 1) begin
            sel = i[1:0];
            #1;
            $display(" %b  | %b", sel, y);
        end
        $finish;
    end
endmodule
`default_nettype wire

Line by line

  • assign y = sel[1] ? (sel[0] ? d[3] : d[2]) : (sel[0] ? d[1] : d[0]); is a tree of three 2:1 multiplexers. The outer select chooses the upper or lower pair; the inner select chooses one bit of that pair.
  • d[3] is bit 3, the most significant bit of d. When sel = 11, the output is d[3].
  • The testbench sets d = 4'b1010, so the bits from 0 to 3 are 0, 1, 0, 1. The expected output for selects 00, 01, 10, 11 is therefore 0, 1, 0, 1.
  • #1 after each select change lets the combinational logic settle before printing. The logic is zero-delay, but the delay makes the sample unambiguous.

The actual run

Simulator output actual run · Icarus 13.0 
d=1010
sel | y
----+--
 00  | 0
 01  | 1
 10  | 0
 11  | 1
example.v:30: $finish called at 4 (1s)

The output follows the bits of 1010 exactly. A wiring mistake in the nested ternary — for example swapping d[2] and d[3] — would still compile and would only be caught by a test that walks the select values, as this one does.

Dataflow, behavioural or gates?

Choosing a style for combinational logic
StyleBest forMain risk
DataflowShort equations, arithmetic, multiplexers, decodersUnreadable nested expressions; multiple drivers
BehaviouralPriority logic, case tables, complex conditionsAccidental latches; incomplete assignments
Gate levelLeaf cells, netlists, exact gate mappingVerbosity; obscures intent

A common professional mix is behavioural always @* for decision logic and dataflow assign for the datapath underneath it. The two styles can coexist in one module as long as each signal has exactly one driver.

A note on latches and loops

Dataflow assignments cannot infer a latch, because a latch is storage and assign has no state. What can go wrong instead is a combinational loop: assign a = ~a; or a cycle of assignments with no register in it. The simulator will evaluate the loop until it settles or reports oscillation; synthesis will reject it or produce a circuit that does not match the simulation.

Accidental latches belong to procedural code, where an if without an else leaves a variable unassigned on some paths. That is covered in the behavioural unit; do not look for it in assign.

Common mistakes

  • Assigning to a reg. assign drives nets. Use wire, or move the logic into an always block.
  • Expecting source order to matter. Continuous assignments are concurrent. Reordering them changes nothing.
  • Driving one net from two assign statements. The result is contention and x, not a priority encoder.
  • Misreading a nested conditional. Add parentheses and, if the tree is deeper than two levels, consider a case statement instead.
  • Using #delay in synthesizable dataflow. It is ignored or rejected; timing is not created by annotation.
  • Building a combinational loop. Feedback must pass through a register, or the circuit has no stable state.

Revision points

  • assign creates a permanent combinational connection and re-evaluates on input changes.
  • Continuous assignments are concurrent and order-independent.
  • The conditional operator ? : describes a multiplexer; nested uses are right-associative.
  • Dataflow cannot store state and cannot infer a latch; feedback without a register is a combinational loop.
  • One driver per net; two drivers produce contention.
