Behavioural Modelling

Unit overview

Two procedural constructs, two jobs

Verilog has exactly two procedural constructs: initial and always. Both contain statements that execute in sequence, and both start at time zero during elaboration. The difference is what happens next. An initial block runs its statements once and then stops forever. An always block runs its statements once and then starts again, endlessly, for as long as the simulation lasts.

Neither keyword says anything about hardware on its own. The hardware comes from what the block contains. An always @* block is combinational logic; an always @(posedge clk) block is a register; an initial block is usually a testbench or an FPGA power-up initialisation.

Without a timing control, an always block never yields

This is the single most important rule in the topic. If an always block has no timing control — no @(...), no #delay, no wait — it executes its body, reaches the end, and immediately starts again at the same simulation time. Nothing can stop it, no other process gets a turn, and the simulator appears to hang.

Infinite loop at time zerodo not run this
always begin
    count = count + 1;   // no @, no #, no wait: loops forever at t = 0
end

A combinational always block avoids the trap with a sensitivity list, usually @*, which means "re-run when any signal read by this block changes". A clocked block uses @(posedge clk) or @(negedge clk). A testbench clock generator uses a delay: always #5 clk = ~clk;.

Which construct belongs where

Choosing between initial and always
UseConstructSynthesizable?
Testbench stimulus, one-shot setupinitialNo (simulation only)
Clock and reset generation in a testbenchalways with a delayNo
Combinational logic in RTLalways @*Yes
Registers in RTLalways @(posedge clk)Yes
Power-up values in an FPGAinitial on a regFPGA-specific, not ASIC

The FPGA row is a real exception that must not be generalised. Most FPGA tools can initialise a register from an initial block because the bitstream configures every register at power-up. An ASIC has no such mechanism: its registers come out of reset in an unknown state, so every design needs an explicit reset strategy. Writing initial in RTL that must also synthesise for an ASIC is therefore a portability bug, even if the FPGA build works.

A clock, a counter and a stimulus block

The example is a complete self-contained testbench. One always generates the clock, a second always implements a synchronous counter, and the initial block applies reset, waits, and prints samples.

example.v 
`default_nettype none
`timescale 1ns / 1ps

module initial_always_tb;
    reg       clk;
    reg       reset;
    reg [2:0] count;

    // One clock generator for the whole simulation.
    always #5 clk = ~clk;

    // Synchronous counter: runs on every rising edge.
    always @(posedge clk) begin
        if (reset)
            count <= 3'd0;
        else
            count <= count + 3'd1;
    end

    // One-shot stimulus and observation.
    initial begin
        clk   = 1'b0;
        reset = 1'b1;
        count = 3'd0;
        $display("t=%0t initial: clk=%b reset=%b count=%0d", $time, clk, reset, count);

        #12 reset = 1'b0;
        $display("t=%0t initial: reset released", $time);

        #14 $display("t=%0t sample: count=%0d", $time, count);
        #10 $display("t=%0t sample: count=%0d", $time, count);
        #10 $display("t=%0t sample: count=%0d", $time, count);

        $finish;
    end
endmodule
`default_nettype wire

Line by line

  • always #5 clk = ~clk; has no sensitivity list. The delay is the timing control: wait 5 ns, invert the clock, repeat. That gives a 10 ns period, a 100 MHz clock in this timescale.
  • always @(posedge clk) runs its body once at every rising edge and then waits for the next one. It is a register, because it stores count between edges.
  • if (reset) count <= 3'd0; makes reset synchronous: the counter is cleared on the next clock edge, not immediately when reset goes high.
  • count <= count + 3'd1; describes a three-bit counter. It wraps from 7 to 0 naturally because the destination is three bits.
  • The non-blocking assignments matter here. If the two branches used blocking assignments, the counter would still work in this simple case, but mixing styles across a design is how race conditions start. The next topic explains why in detail.
  • initial begin ... end runs once at time zero. It initialises the clock and reset, then uses delays to schedule later actions.
  • #12 reset = 1'b0; releases reset at 12 ns, which is between two rising edges. The counter therefore starts incrementing at the edge at 15 ns.
  • #14 $display(...) at 26 ns samples the value set at the edge at 25 ns. The later samples at 36 and 46 ns follow the same pattern.
  • $finish ends the simulation. Without it, the clock generator would keep the event queue alive forever.

The actual run

Simulator output actual run · Icarus 13.0 
t=0 initial: clk=0 reset=1 count=0
t=12000 initial: reset released
t=26000 sample: count=2
t=36000 sample: count=3
t=46000 sample: count=4
example.v:34: $finish called at 46000 (1ps)

Follow the time line:

  • t = 0: both blocks start. The clock is 0, reset is 1, count is 0. The first rising edge is at 5 ns.
  • t = 5 ns: reset is still high, so the counter loads 0 again.
  • t = 12 ns: reset is released. This is not a clock edge, so nothing is stored yet; the message is printed by the initial block.
  • t = 15 ns: the first rising edge with reset low. count becomes 1.
  • t = 25 ns: count becomes 2. The sample at 26 ns reads 2.
  • t = 35 ns: count becomes 3; the sample at 36 ns reads 3.
  • t = 45 ns: count becomes 4; the sample at 46 ns reads 4.

The printed times are 7000, 12000 and so on because %0t formats in the simulation precision, 1 ps. Twelve nanoseconds is 12000 ps.

Sensitivity lists and @*

Before Verilog-2001, a combinational block had to list every input by hand: always @(a or b or sel). Forgetting one produced a simulation that behaved differently from synthesis, because the block simply did not re-run when the missing signal changed. Verilog-2001 introduced @* (and the equivalent @(*)), which infers the list from the signals read inside the block.

  • Use always @* for combinational logic. It removes an entire class of stale-sensitivity bugs.
  • Use an explicit edge list for sequential logic. @* must never be used for a register, because it would trigger on data changes as well as clock edges.
  • @* includes signals read in the block, not signals written. A signal that only appears on the left-hand side is not an input.

Common mistakes

  • An always block with no timing control. It loops forever at time zero and the simulation hangs. Every always needs @, # or wait.
  • Using initial in ASIC RTL. It is not synthesizable there. Use a reset. FPGA initialisation works but does not port.
  • Using @* for a register. The block then triggers on data transitions, which is not a flip-flop.
  • Forgetting $finish in a testbench. A free-running clock keeps the simulation alive until the tool's time limit.
  • Assuming initial runs before always. Both start at time zero; the order between them is not defined by the language. Never rely on it.
  • Treating a synchronous reset as asynchronous. if (reset) inside @(posedge clk) takes effect at the next edge, not immediately. Asynchronous reset needs or negedge reset in the sensitivity list and its own timing analysis.

Revision points

  • initial runs once; always repeats forever and must contain a timing control.
  • always @* describes combinational logic; always @(posedge clk) describes registers.
  • A testbench clock generator is always #5 clk = ~clk; — simulation only.
  • initial is not synthesizable for ASIC; FPGA power-up initialisation is a vendor-specific exception.
  • Both constructs start at time zero, and their relative order is undefined.
