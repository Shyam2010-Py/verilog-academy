Unit overview

One module, many sizes

A parameter is a constant that is fixed when a module is elaborated. It lets one module definition serve several widths, depths or modes without copying the source. A local parameter is the same idea with one extra restriction: it cannot be overridden from outside.

Parameters are not signals. They do not exist in the hardware as wires or registers; they disappear into the structure of the circuit that elaboration builds. Changing a parameter changes the circuit, not the value stored in it.

Parameter versus localparam

Two kinds of constant

The naming convention matters for review. A parameter is part of the module's contract: a parent is allowed to change it. A localparam is an implementation detail. If a value must stay consistent inside the module — a derived width, a state encoding, a fixed depth — make it a localparam so no parent can break the invariant by accident.

Three ways to override

  • Positional: width_demo #(6) u (...); overrides parameters in declaration order. Compact, but fragile if the parameter list changes.
  • Named: width_demo #(.WIDTH(6)) u (...); states exactly which parameter changes. This is the professional default.
  • defparam: defparam u.WIDTH = 6; overrides through a hierarchical path. It is legal Verilog-2001 but legacy, hard to trace, and poorly supported by some synthesis flows. Use the #(...) form in new code.

Verilog-2001 allows the parameter list in the module header, before the port list: module m #(parameter WIDTH = 4) (...);. That keeps the contract next to the ports, where a reader will see it.

A width parameter in action

One module produces a repeating two-bit pattern. The number of repetitions is derived from WIDTH, and the output is a fixed eight bits so the effect of each override is visible in one place.

example.v 
`default_nettype none
// WIDTH can be overridden; HALF cannot.
module width_demo #(parameter WIDTH = 4) (
    output wire [7:0] pattern
);
    localparam HALF = WIDTH / 2;

    assign pattern = {HALF{2'b10}};
endmodule

module parameters_tb;
    wire [7:0] p_default;
    wire [7:0] p_override;
    wire [7:0] p_defparam;

    width_demo u_default  (.pattern(p_default));
    width_demo #(.WIDTH(6)) u_override (.pattern(p_override));
    width_demo u_defparam (.pattern(p_defparam));

    // Legacy hierarchical override. Prefer #(...) in new code.
    defparam u_defparam.WIDTH = 8;

    initial begin
        #1;
        $display("default  WIDTH=4 -> %b", p_default);
        $display("named    WIDTH=6 -> %b", p_override);
        $display("defparam WIDTH=8 -> %b", p_defparam);
        $display("hierarchical parameter value: %0d", u_override.WIDTH);
        $finish;
    end
endmodule
`default_nettype wire

Line by line

  • module width_demo #(parameter WIDTH = 4) ( puts the parameter in the header. A parent that says nothing gets WIDTH = 4.
  • localparam HALF = WIDTH / 2; derives the repetition count. A parent cannot override HALF; it can only change WIDTH, and HALF follows.
  • assign pattern = {HALF{2'b10}}; replicates 10 exactly HALF times. With WIDTH = 4, HALF = 2, so the result is four bits; the eight-bit output is zero-extended to 00001010.
  • width_demo u_default (.pattern(p_default)); uses the default width.
  • width_demo #(.WIDTH(6)) u_override (...); changes the parameter by name. HALF becomes 3, the pattern becomes six bits, and the output is 00101010.
  • defparam u_defparam.WIDTH = 8; shows the legacy override. It changes the same parameter through the instance path; HALF becomes 4 and the pattern fills all eight bits.
  • u_override.WIDTH is a hierarchical read of the elaborated parameter value. Simulation tools support it; not every synthesis flow does.

The actual run

Simulator output actual run · Icarus 13.0 
default  WIDTH=4 -> 00001010
named    WIDTH=6 -> 00101010
defparam WIDTH=8 -> 10101010
hierarchical parameter value: 6
example.v:29: $finish called at 1 (1s)

Read the three patterns together. The default produces two repetitions in an eight-bit field; the named override produces three; the legacy override produces four. The hierarchical read prints 6 because u_override was overridden by name, not by defparam.

Parameterised interfaces

Parameters become genuinely useful when port widths depend on them. A parameterised adder might declare input [WIDTH-1:0] a and output [WIDTH:0] sum; every instance then agrees on the width because the parent passes one value. Two rules keep this safe:

  • Derive every dependent width from the same parameter, preferably through localparams. Do not repeat magic numbers in port declarations.
  • When a parent overrides a width, it must also size the nets it connects. A parameterised module does not resize its parent's wires.

Common mistakes

  • Trying to override a localparam. It is fixed by the module. The tool will reject the override or ignore it, depending on the flow.
  • Using positional overrides after editing the parameter list. Every instance silently shifts. Use named overrides.
  • Using defparam in new RTL. It is hard to find, interacts badly with hierarchy changes, and is not accepted everywhere.
  • Treating a parameter as a signal. It cannot be assigned in an always block and does not appear in a waveform.
  • Forgetting to resize the parent's nets. A parameterised module can be instantiated with a wider port than the wire connected to it; the connection truncates.
  • Making an internal constant a parameter. If a parent should not change it, a localparam documents that intent and prevents the mistake.

Revision points

  • Parameters are elaboration-time constants; they are part of the module contract and can be overridden.
  • Localparams are internal constants and cannot be overridden.
  • Prefer named overrides #(.WIDTH(6)); avoid positional overrides and defparam in new code.
  • Derive dependent widths from one parameter so the interface stays consistent.
  • Parameters do not exist as hardware signals.
